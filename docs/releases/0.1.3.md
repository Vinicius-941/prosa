# Prosa 0.1.3 — registro de validação e preparação

O workflow `Prosa release` valida o código e compila pacotes Windows, Linux e Android quando a tag `v0.1.3` é enviada. A publicação só ocorre após todos os builds concluírem com sucesso.

## Incluído nesta preparação

- Agrupamento das conversas diretas, do espaço pessoal e dos canais, com contexto da comunidade e remoção da duplicação de canais.
- Fluxos de criação e entrada por convite em diálogos separados, com foco acessível; criar comunidade abre o canal `geral`.
- Ações de gestão da comunidade ficam agrupadas em painel expansível; participantes comuns veem a lista sem controles administrativos.
- Convite inválido ou falha de rede mantém o diálogo aberto, mostra erro junto ao campo e preserva o código para correção.
- Barras de rolagem visíveis em áreas roláveis da interface.
- Trocar de conversa ou voltar à tela de mensagens abre no fim do histórico; carregar mensagens antigas mantém a posição de leitura.
- Ações de mensagem permanecem fora do balão seguinte ao redimensionar janelas; telas sem hover mantêm Editar e Remover acessíveis por toque.
- Quando a conexão de rede volta, o socket é reiniciado para restabelecer a sincronização em tempo real.
- Espaço pessoal e canais sem mensagens agora explicam como começar.
- Avisos de sucesso não bloqueiam os controles que ficam sob o toast.
- Contexto de canais em Recentes respeita a largura da sidebar em 768 px e usa truncamento quando necessário.
- Edição de nome, identificador público, descrição simples e opções limitadas de cor/moldura do avatar. Migração SQLite aditiva preserva contas existentes.
- Prévia do perfil usa o mesmo componente de avatar e as mesmas iniciais exibidas no restante do app.
- A identidade (cor e moldura) propaga entre busca, contatos, participantes, conversas e mensagens, com atualização em tempo real após editar o perfil.
- No Electron, sessão cifrada com `safeStorage`; no Android, token cifrado com AES-GCM sob Android Keystore. Ambos migram gradualmente a sessão antiga; Linux exige chaveiro compatível.
- No navegador, sessão em cookie HttpOnly, pedidos de alteração protegidos por CSRF e validação de origem; sessões antigas migram automaticamente. Cliente e API precisam compartilhar o mesmo site/domínio de implantação.
- Sockets em sessões que vencem são encerrados no vencimento; o app limpa o token, mostra aviso e retorna ao login.
- Configurações identificam a plataforma, oferecem preferência persistente de animações reduzidas e inicialização automática real no Windows/Linux.
- Relatório de auditoria de interface e segurança, incluindo limitações da pesquisa visual e riscos residuais.
- Matriz rota a rota HTTP e eventos Socket.IO, com regra de acesso, testes existentes e lacunas conhecidas em [authorization matrix](../security/0.1.3-authorization-matrix.md).
- Evento de saída de sala ignora payloads inválidos sem remover a sessão da sala autorizada; teste de integração cobre nulo, objeto, número e ID longo.
- Sinais de chamada limitados a 100 por conta em 10 segundos, agregados entre sockets, com teste de integração para rajada e segundo socket.

## Validação local

- `npm test` — 2 testes passaram, incluindo expiração de socket autenticado, autorização social, migração de banco legado, flags Secure/HttpOnly dos cookies de produção, bloqueio CSRF, logout web, formatação segura da entrada Linux, payloads inválidos de `conversation:leave` e limite de sinais de chamada agregado entre sockets.
- `npm run test:e2e` — passou no Chromium, incluindo regressão de rolagem ao trocar conversas, estados vazios do espaço pessoal, canal e comunidades verificados por axe, assert contra colisões dos controles de mensagem após redimensionamento em 768 px, edição por toque em 320 px, reconexão depois de offline/online, promoção, remoção de participante/admin, saída, renomeação e exclusão comunitária com cancelamento/confirmação, convite inválido com recuperação inline, criação de canal pelo administrador, edição do perfil, larguras amostradas e densidades/reflow ampliado simulados em 100/125/150%.
- E2E confirma que o cadastro web não devolve nem persiste token em `localStorage`, valida cookies HttpOnly, migra sessão legada e rejeita alteração sem CSRF.
- `npm run build` — passou.
- `npm run package:desktop` — recompilou a interface e o serviço, empacotou Windows e iniciou com perfil temporário explícito; a tela de cadastro foi renderizada e a API local respondeu HTTP 200 em [windows-registration-fixed-0.1.3.png](../research/screenshots/windows-registration-fixed-0.1.3.png). O harness verificou cadastro isolado, API, largura sem overflow e leitura/alternância da inicialização nativa, restaurando a preferência original; a captura da configuração está em [windows-settings-startup-0.1.3.png](../research/screenshots/windows-settings-startup-0.1.3.png). O pacote também foi renderizado via CDP com densidade simulada 100/125/150%, sem overflow horizontal do documento.
- `npm run android:sync` e `gradlew assembleDebug` — passaram para o código atual usando o JDK do Android Studio. APK instalado e aberto no emulador Android 16 (API 36); formulário de cadastro renderizado e capturado após 12 segundos. Inspeção da WebView confirmou a árvore React e os recursos carregados. O bridge Keystore confirmou round-trip AES-GCM, rejeição de token inválido, ausência em `localStorage`, ciphertext nas preferências e limpeza após logout.
- O workflow de release compila os pacotes `.deb` e AppImage em Linux nativo, além do instalador Windows e APK Android; validações do PR cobrem esse build Linux. O smoke headless confirma janela e API, mas não autentica nem verifica as preferências do Linux porque o executor não fornece um chaveiro desbloqueado.
- QA reproduziu uma janela vazia quando `electron-builder` foi executado após o build web, que usa caminhos incompatíveis com `file://`. O CI fazia essa mesma sequência; foi corrigido para executar `npm run build:desktop` antes do empacotamento. O fluxo suportado `npm run package:desktop` foi refeito e o binário Windows abriu corretamente.
- `npm run lint` — passou.
- `npm audit --omit=dev` — 0 vulnerabilidades; auditoria completa atual mantém 8 moderadas na cadeia de build do Electron, incluindo `sprintf-js@1.1.3`; npm ainda só oferece `electron-builder@26.5.0` como alteração, um downgrade sem correção específica confirmada.

Capturas de referência do Chromium, Windows isolado e Android API 36 ficam em [screenshots](../research/screenshots/). No Android, o teclado foi aberto e a tela rolada até os campos finais: [cadastro](../research/screenshots/android-registration-api36-current.png), [teclado](../research/screenshots/android-registration-keyboard-api36.png), [formulário rolado com teclado](../research/screenshots/android-registration-keyboard-scroll-api36.png). Densidade, reflow e zoom foram simulados; DPI nativo 100/125/150%, zoom real do navegador, Linux nativo e dispositivo Android físico ainda não foram testados.

## Ainda bloqueia o aceite desta versão

- Pesquisa Refero não concluída: resposta recebida `NO_SUBSCRIPTION` (assinatura inativa ou expirada). Ver [pesquisa e auditoria](../research/prosa-0.1.3-design.md).
- Navegadores com bloqueio estrito de cookies de terceiros podem exigir publicação da interface e API sob o mesmo site/domínio.
- Tema, comportamento ao fechar e notificações globais ainda sem suporte.
- Validação de login e preferências Linux com chaveiro real, Android físico, Windows com escalas 100/125/150%, zoom do navegador e texto ampliado ainda pendente.
- A administração continua na página de detalhes; transferência de responsabilidade e recuperação de falhas de rede durante cada mutação ainda precisam de cenários próprios.
